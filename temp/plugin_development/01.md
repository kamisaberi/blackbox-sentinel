### Extensibility Architecture & Tiered Execution Model

To maintain the $< 1.0\,\mu\text{s}$ edge mitigation invariant while opening the engine to third-party developers, the Sentinel Extensibility Framework adopts a **3-Tier Execution Model**. Each execution tier targets a distinct balance between line-rate execution speed and memory-safety sandboxing:

```text
========================================================================================================
                               SENTINEL 3-TIER EXTENSIBILITY ARCHITECTURE
========================================================================================================

  INCOMING PACKET / EVENT (From Lock-Free SPMC EventRingBuffer)
                            │
                            ▼
                [ PluginSupervisor Dispatcher ]
                            │
         ┌──────────────────┼──────────────────────────────┐
         ▼                  ▼                              ▼
  [ TIER A: NATIVE C++20 ]   [ TIER B: WASM SANDBOX ]       [ TIER C: LUAJIT ENGINE ]
  • ABI: C Foreign Function  • Runtime: Wasm3 / Wasmtime    • Engine: LuaJIT 2.1 (JIT Traced)
  • Latency: < 120 ns        • Latency: 1.2 µs - 2.8 µs     • Latency: < 450 ns
  • Security: Process-Native • Security: Linear Memory VM   • Security: Lua State Sandbox
  • Use Case: Line-rate OT   • Use Case: Untrusted 3rd-Party• Use Case: 10-line Zero-Day Rules
    Dissectors (S7, GOOSE)     Community Marketplace Plugins  Hot-Reloaded via inotify / Nexus
         │                  │                              │
         └──────────────────┴──────────────┬───────────────┘
                                           ▼
                    [ Unified Dissector Verdict & Telemetry ]
                    (PASS | ALERT | DROP_KERNEL | DIVERT_HONEYPOT)
========================================================================================================
```

## 2. Core Technical Specifications

### 2.1 Native C++20 Header-Only SDK (`<sentinel/sdk/plugin.hpp>`)
* **Strict C ABI Boundary:** Dynamic libraries export exactly one entry point:
  ```cpp
  extern "C" ARY_EXPORT const SentinelPluginDescriptor* sentinel_plugin_init(const SentinelHostInterface* host);
  ```
* **Zero Allocation Contract:** Plugins accept `PacketView` (raw pointer + length). Allocating on the heap (`malloc`, `new`, `std::vector`) within the line-rate hot path is strictly prohibited via custom static assertion guidelines.
* **Symbol Scoping:** Plugins must be built with `-fvisibility=hidden`. Only `sentinel_plugin_init` is exported.

### 2.2 Embedded WebAssembly (Wasm) Micro-Sandbox
* **Engine Choice:** **Wasm3** (Ultra-fast, interpreted, $< 100\,\text{KB}$ binary footprint, zero JIT compilation latency) for low-memory appliances; switchable to **Wasmtime** on multi-core appliances.
* **Memory Isolation:** Each Wasm module runs inside an isolated $64\,\text{KB}$ - $4\,\text{MB}$ linear memory page. The host copies the frame header into Wasm linear memory at offset 0, executes `dissect()`, and retrieves the 64-bit verdict integer.
* **Gas / Instruction Limit:** Strict execution quota ($50{,}000$ instructions max per frame). Infinite loops in third-party code trigger an instant trap and module quarantine.

### 2.3 LuaJIT Dynamic Hot-Reload Engine
* **Runtime:** LuaJIT 2.1 with trace-compiler optimizations.
* **Hot-Reload Trigger:** Linux `inotify` watches `/etc/sentinel/rules.d/`. Saving a new `threat_*.lua` file recompiles and swaps the bytecode state in $< 2\,\text{ms}$ with zero daemon restart or packet loss.
* **FFI Bindings:** Direct pointer binding (`ffi.cdef`) allowing Lua to inspect packet memory buffers with zero copy.

  ├── Step 3.1: Embed Wasm3 runtime into src/sdk/WasmSandbox.cpp.

  ├── Step 4.1: Build PluginSupervisor to chain Native -> Lua -> Wasm evaluation pipelines.
  ├── Step 4.2: Add gRPC hot-staging in Nexus to push signed Lua/Wasm rules fleet-wide in < 50ms.
  └── Step 4.3: Implement CLI utility (sentinel-plugin-pack) for packaging and signing .splugin files.
